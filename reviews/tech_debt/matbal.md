# Tech Debt — matbal

Scope: TECH DEBT only. Correctness and API/UX issues live in the sibling review files and are not re-flagged here.

## High

### H1. Duplicated Efw/denom/N-mean arithmetic — `_compute_result` vs `objective` Python fallback
Location: `matbal.py:544-557` and `matbal.py:596-612`.
Three separate implementations of the same calculation now co-exist:
1. `_compute_result(m_t, cf_t, cw_t, sw_t)` — vectorised NumPy (final pass).
2. The Python fallback inside `objective(x)` — **scalar loop** over `i in range(n)` to compute the same `Efw_t`, then reproduces the same `denom_t = Eo + m*Eg + (1+m)*Efw_t` and `mean/std` math.
3. `_rust.matbal_objective_rust` — the accelerated mirror.
The scalar Python loop (line 600) does not even match the vectorised shape in `_compute_result`. One helper, e.g. `_compute_denom_and_N(m, cf, cw, sw_i) -> (N_estimates, ooip, denom, Efw)`, would let `objective` call it and return `std(N)/abs(mean(N))`, eliminating the triple-maintenance burden. Any correctness fix (e.g. the `(1+m)*Efw` question raised in correctness #2) currently requires edits in 3 places + the Rust source.

### H2. Silent Rust-fallback pattern in `objective`
Location: `matbal.py:586-595`.
Ad-hoc try/except around `_rust.matbal_objective_rust` is the exact pattern the `@rust_accelerated` decorator (`_accelerator.py:187`) was introduced to replace across the codebase. Tier-3 roadmap item T3-5 migrated 8 nodal VLP functions to the decorator but skipped this site. The objective closure captures free variables (F, Eo, Eg, p_field, Boi, base_vals, param_names, n), so it is not a one-liner migration, but the *pattern* remains inconsistent with the rest of the codebase and swallows `ImportError`/`AttributeError` without logging or warning. (Correctness file flags the user-visible effect; the tech-debt issue is the divergence from project convention.)

## Medium

### M1. Dead/unused imports
Location: `matbal.py:43, 48`.
- `List` imported from `typing`, never used.
- `PSI_TO_BAR` imported from `pyrestoolbox.constants`, never used (all conversions in the file go via `/ BAR_TO_PSI`).
Trivial to remove; they survived the split because nothing fails.

### M2. Missing `validate_pe_inputs` at public entry points
Per Tier-1 "New Code Requirements", `validate_pe_inputs` is mandatory after metric-to-oilfield conversion. Neither `gas_matbal` (entry at 140) nor `oil_matbal` (entry at 336) calls it. This is a matbal-wide drift from a convention that other modules (gas rate/hydrate, brine init, nodal fbhp, all oil public fns) now enforce. Flagged under API/UX too but the *tech-debt angle* is: convention is now enforced elsewhere, so matbal will be the lone outlier and will surface on future grep audits.

### M3. Inline correlation constants / magic numbers
Per Tier-1 "Named Constants":
- Line 496: `sg_o = 141.5 / (api + 131.5)` — API-to-SG formula is duplicated throughout oil-module code; should use a shared helper or named constants (`_API_A = 141.5`, `_API_B = 131.5` — these live in `oil/_constants.py` already; matbal re-inlines them).
- Lines 280, 301, 308, 541, 552, 605: `1e-30` is used six times as a zero-guard with no named constant (e.g. `_DENOM_EPS`).
- Lines 245, 484: `1e-6` bracket tolerance for pvt_table range check, duplicated.
- Lines 607, 611: `1e10` sentinel objective value for degenerate regression — unnamed, not documented.

### M4. Type-hint gap on public API
Location: `matbal.py:140, 336`.
`gas_matbal(p, Gp, degf, sg=0.65, ...)` and `oil_matbal(p, Np, degf, ...)` have no parameter or return-type annotations. The dataclasses are annotated; the functions themselves are not. Other modules (nodal, brine) have moved to annotated signatures. Low-risk cleanup; improves IDE support and static analysis.

### M5. Dataclass field naming inconsistency — lowercase `gp` / `bg` vs PascalCase `F, Et`
Location: `GasMatbalResult` at line 57.
`.gp`, `.bg`, `.pz` are lowercase; `.F`, `.Et`, `.cole_F_over_Et` keep their MB-equation symbol casing. Flagged as UX in API file; the tech-debt concern is that the same class mixes conventions, which grep-search and autogenerated docs treat differently. Cheap to freeze on one style before more fields are added.

## Low

### L1. `_ALLOWED_REGRESS` defined inside function body
Location: `matbal.py:417`.
`_ALLOWED_REGRESS = {'m', 'cf', 'cw', 'sw_i'}` is a module-level constant by intent (uppercase + underscore prefix) but is redefined every call inside `oil_matbal`. Move to module scope near the top of the file.

### L2. `base_vals` dict drift between regression and final paths
Location: `matbal.py:574, 596, 615-621`.
Regression mutates `base_vals` via a for-loop at lines 616-617 (writing the optimizer's `x` back into the dict), then re-reads individual keys into local `m, cf, cw, sw_i` at 618-621. This is an awkward marshalling step caused by having *two* representations of the same parameter set (the dict and the local scalars). Either keep one dict or keep scalars; don't maintain both.

### L3. Test coverage gap — regression branches
`test_matbal.py` covers `test_oil_matbal_regress_m`, `test_oil_matbal_regress_cf`, `test_oil_matbal_regress_multiple`, plus error cases. Gaps:
- No test for regressing `cw` or `sw_i` individually (only `m` and `cf` are exercised).
- No test for the *Python-fallback path* of `objective` (`_RUST_AVAILABLE=False` path). With Rust present locally, line 596-612 is never executed in test; divergence between Python and Rust would go undetected. Set `PYRESTOOLBOX_NO_RUST=1` in a dedicated test run or mock `_RUST_AVAILABLE`.
- No test for the degenerate `1e10` early-return branches (lines 606-607, 610-611).
- No metric-units test for `pvt_table` in either `gas_matbal` or `oil_matbal` (correctness #1 notes the metric-pvt_table bug would have been caught by such a test).

### L4. `import warnings` would be needed but not imported
If the Rust-fallback `warnings.warn` fix from correctness #3 lands, `import warnings` must be added. Currently absent — just a forward-looking note, not a bug today.

### L5. `from scipy.optimize import minimize` imported inside function
Location: `matbal.py:562`.
Lazy import is a deliberate pattern elsewhere in the codebase to defer scipy loading, but since `gas_matbal` already uses `ransac_linreg` (scipy-backed via `shared_fns`), scipy is loaded anyway when matbal is exercised. The local import adds no benefit here and makes the dependency less visible at the top of the file. Low priority.
